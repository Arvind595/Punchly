## How to read the evidence

- A **release marker** identifies the version displayed or generated by a particular commit. From v32, the editable number lives in `release.json`. Earlier snapshots put a marker in the app shell or worker.
- An **archived note** attributes behavior to an app version. Its source link can point to a later commit containing several app versions. A comparison link shows the entire committed change between the named snapshots.
- The v0–v3 sequence and v14–v16 changes are documented in groups. The v13 boundary is unresolved. The v11 timestamp behavior is documented by the historical v12 guide and v12 implementation.

## Inspect the history locally

```sh
git log --first-parent --reverse --oneline
git show 31e6fef:js/statistics.js
git diff 3fe903a 31e6fef -- js/statistics.js js/app.js tests/statistics.test.mjs
git log --oneline -- js/storage.js
```

Use `git show <commit>:<path>` for a file as it stood in a release and `git diff <older> <newer> -- <path>` for the exact implementation delta. To reproduce historical behavior, open that snapshot from a separate working directory with an isolated browser origin or profile. The [test data guide](../../test-data/README.md) describes the retained backups and browser scenarios.

When documenting a later release, link the numbered snapshot and previous-to-current diff, identify the changed code paths, and describe any effects on persisted data or older backups. Link the regression coverage that exists in that snapshot.
